# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

mrowser is a sideload-only Android TV browser (`net.mrowser`) for streaming video. It browses any site with a D-pad-driven virtual mouse cursor, sniffs the page's network traffic for a stream (HLS, DASH, or a plain progressive file), and hands it off to a native Media3/ExoPlayer activity — because the WebView's built-in player gives poor A/V sync. No Google Play Services; single Gradle module `:app`, all Kotlin.

## Commands

```bash
./gradlew test               # unit tests (JVM, no device)
./gradlew testDebugUnitTest --tests "net.mrowser.stream.MediaUrlClassifierTest"   # single test class
./gradlew assembleDebug      # debug APK   -> app/build/outputs/apk/debug/
./gradlew assembleRelease    # signed APK  -> app/build/outputs/apk/release/  (needs keystore.properties; unsigned if absent)
```

Toolchain: JDK 17, AGP 9.1.1 (built-in Kotlin), Gradle 9.3.1. `compileSdk 36` / `minSdk 23` / `targetSdk 34`. Needs SDK packages `platforms;android-36` and `build-tools;36.0.0`. Versions are pinned in `gradle/libs.versions.toml` (version catalog) — change deps there, not in `app/build.gradle.kts`.

## Architecture

Two activities (`AndroidManifest.xml`), wired in `MainActivity.onCreate`:

- **MainActivity** — the browser. Hosts a `WebView` inside a custom `CursorLayout`, plus the chrome bar and the home screen overlay. It is also **registered as a system browser** (`ACTION_VIEW` + `BROWSABLE`/`DEFAULT` on `http`/`https`, plus `CATEGORY_APP_BROWSER` on the launcher filter), so links from other apps offer mrowser in the chooser; `launchMode="singleTask"` + `onNewIntent` make such a link navigate the running page instead of stacking a second browser. The incoming URL is vetted by the **pure** `IncomingUrl` — **http/https only**, because the WebView would also resolve a `file:`/`content:`/`javascript:` URL any app on the box could send it.
- **PlayerActivity** — the native player. Handoff is **automatic** when a stream is detected — unless the **Auto-open synced player** setting is off, in which case only the play chip shows and the user activates it; launched with a serialized `PlaybackRequest` Intent extra. **BACK hides the controls first** — media3's `PlayerView` does not consume BACK, so with the controller fully visible `onBackPressed` calls `hideController()` and stays; with it hidden, **BACK returns to the browser** (the WebView is paused during playback via `onPause`/`onResume`). The play-synced chip re-enters the player and auto-hides after 30s, and re-entry **resumes where the stream was left** (see `player/` below). Quality / Audio / Speed live in the player's **built-in settings gear** — its click is overridden in `showSettings` (media3 has no public hook, so it reuses `androidx.media3.ui.R.id.exo_settings`). **Subtitles are app-rendered, not player-rendered** (so their timing can be nudged live — see `player/` below): the **sub-sync box** (top-left, shown with the controls) holds a `CC` button (on/off + track picker) and `− Subtitle delay ±X.Xs +` offset buttons (±0.5s/press, clamp ±30s, reset per stream; a true minus sign, so the tabular figures keep the box from shifting). It is a 40dp capsule with 5dp padding all round, so its 30dp buttons sit concentric; −/+ are `ic_minus`/`ic_plus` vectors in `ImageButton`s (text glyphs sat off-centre), CC is the `ic_cc` badge tinted accent while subtitles show (on the white focus disc too) — `updateSubsButton`; media3's own CC button is hidden because it greys out with no player text track. Finishes (back to the browser) on any playback error. Holds `FLAG_KEEP_SCREEN_ON` **only while playing** (toggled in `onIsPlayingChanged`) — TV gets no input events mid-movie, so without it the system sleep timeout fires; a paused stream can still sleep. **Display-mode matching** (both opt-in, off by default — most TVs blank for a moment on a switch): with **Match frame rate** and/or **Match resolution** on, the first time a stream's video tracks are known the **pure** `DisplayModeMatcher` picks a `Display.Mode` and the window asks for it via `WindowManager.LayoutParams.preferredDisplayModeId` (API 23, and unlike media3's `setVideoChangeFrameRateStrategy` — left at its default — it also switches resolution and is not limited to seamless changes). Resolution first (exact size, else the smallest mode that holds the video, else the current size), then the rate within that size (exact within 0.01 Hz per multiple, else the smallest integer multiple; never a non-multiple, so 23.976 never takes 24 or 120). Unknown fps changes no rate. The target is the **largest** selected rendition (adaptive HLS starts small), borrowing an fps from any rendition that declares one; if the tracks carry none (HLS without `FRAME-RATE`) and rate matching is on, it waits for the decoder's `videoFormat` at the first frame (`onVideoSizeChanged`) before settling. Runs once per stream; `onStop`/`onDestroy` put the window's original preference back and `onStart` re-asks. Settings are read from `settings.json` when the tracks arrive (a read-only `JsonSettingsStore`), so a toggle applies to the next stream. `configChanges` includes `smallestScreenSize|screenLayout|density` so a resolution switch can't recreate the player.

Code is split by domain under `net.mrowser.*`, and within each domain **pure logic is separated from Android-dependent code so it can be unit-tested without a device**. The pure pieces are the ones with tests in `app/src/test/`. When adding logic, follow this split: put decision/parsing/geometry in a plain object/class and keep the Android glue thin.

### `stream/` — stream detection and handoff
The core pipeline:
1. `SniffingWebViewClient` forwards every `WebView` resource request to `StreamSniffer`, together with the request headers the WebView reports for it (`WebResourceRequest.requestHeaders`). It also overrides `shouldOverrideUrlLoading` to route non-web navigations out of the WebView — see `ExternalSchemePolicy` under `web/`.
2. `StreamSniffer` (thread-safe; called off the UI thread) classifies each URL via the **pure** `MediaUrlClassifier` (extension-based: `.m3u8`→HLS, `.mpd`→DASH, `.mp4`/`.m4v`/`.webm`/`.mkv`→progressive, `.vtt`/`.srt`→subtitle, etc.) and accumulates `StreamCandidate`s. `.mp4` is **both** a whole file and the segment container of fMP4 HLS/DASH, and a resource request carries no Content-Type, so the filename decides: a role name (`init`, `seg`, `chunk`, `frag`, `dashinit`), a bare number, or a zero-padded trailing number is a `SEGMENT`; anything else (`Solaris.1972.1080p.mp4`) is `PROGRESSIVE`.
3. A manifest fires `onStreamAvailable` at once (shows the play chip, triggers handoff). A progressive file is the **weakest** signal — a page that also serves a manifest may request a preview clip first — so it announces only after a 1.5s grace window, scheduled through the injected `schedule` lambda (a main-looper `Handler` in `MainActivity`, so the sniffer itself stays Android-free) and dropped if the page changed meanwhile. The announce-once gate makes a manifest arriving inside that window win the handoff for free.
4. `bestRequest()` uses the **pure** `StreamCandidateSelector` to pick the stream + subtitle tracks, attaches headers, and returns a `PlaybackRequest`. Selection is tiered — HLS (master playlist preferred) → DASH → progressive — so an `.mp4` is only ever the fallback for a page that serves no manifest at all; ad hosts are filtered out of every tier. The headers come from the **pure** `PlaybackHeaders`: User-Agent, plus the **Referer and Origin the WebView itself sent for the chosen stream** (#51). Embedded players run in a cross-origin iframe and their CDNs gate on the *iframe's* origin (`*.vkvideo.cloud` 403s any other `Origin`, or none), so the top page is the wrong Referer. An Origin the WebView did not report is derived from the sniffed Referer when the stream is cross-origin to it. A candidate with no captured headers gets exactly the old pair: top-page Referer, no Origin. Nothing else captured is replayed — page-set headers are often per-request signatures — and Cookie is never taken from the capture: `bestRequest` adds it from `CookieManager`, and `PlayerActivity` re-resolves it per request host.
5. `HandoffController` serializes the `PlaybackRequest` to JSON and starts `PlayerActivity`, which declares the container via the **pure** `MediaMimeType` (`.m3u8`→`application/x-mpegURL`, `.mpd`→`application/dash+xml`, else null so `DefaultMediaSourceFactory` reads the file itself) — a MIME type rather than the URL, because a query string can hide the extension the factory would otherwise guess from.

Side-loaded subtitles carry no language metadata, so the **pure** `SubtitlePlan` labels each sniffed track from its URL via the **pure** `SubtitleLang` (a real name like English/Persian when a language token is found in the path/query/filename — host ignored — else a generic `Subtitle N`). There is intentionally **no** preferred-language setting — a side-loaded track's language can't be known reliably across sites.

### `player/` — native playback + live subtitle sync
media3 has **no public API to offset subtitle timing live**, so `PlayerActivity` gives ExoPlayer **no text track** at all (`buildMediaItem` sets no subtitle configs) and the app renders side-loaded subtitles itself. The **pure** `SubtitleCueParser` (VTT **and** SRT → `SubtitleCue`s, unit-tested) and **pure** `ActiveCueFinder` (cues active at a time, start-inclusive/end-exclusive) do the logic; `SubtitleSyncController` (Android glue) lazily fetches the selected track (`SubtitleFetcher`, with the playback headers), then a ~150ms `Handler` ticker pushes the cues active at `currentPosition + offsetMs` into the player's `SubtitleView`. Because the controller owns cue emission, the sub-sync box's ±0.5s nudge applies **instantly with no rebuffer**. Auto-selects the first track; offset/selection survive a background round-trip via `resume()` (wired to `onStart`); the box hides when a stream has no subtitles. Embedded/HLS-muxed text tracks are intentionally dropped (these sites use side-loaded VTT, which are the ones needing sync).

**Local files.** A finished download plays from its `content://` URI (`file://` too), which only media3's `DefaultDataSource` opens, so `PlayerActivity` wraps its HTTP factory in one **for those schemes only**: a web stream keeps the http-only factory, because `DefaultDataSource` would also follow a `file:`/`content:`/`asset:` URI a hostile manifest lists and read local data.

**Resume.** BACK finishes `PlayerActivity` and every handoff starts a new one, so the position lives outside it: the **pure** `ResumePositions` (an in-memory LRU of 20, keyed by the exact `PlaybackRequest.url`, **process lifetime only — nothing on disk**) held in the `PlayerActivity` companion. `onStop` records `currentPosition` before anything is released; it keeps a position only for a non-live stream with a known duration, past the first 10s and before the last 30s, and otherwise forgets the stream (too early is not worth resuming, the end counts as finished). `STATE_ENDED` clears it too. A stop before the timeline loaded (`duration == C.TIME_UNSET`) leaves the entry alone, so backing out while a resume is still buffering does not lose it. The next open passes the saved position to `setMediaItem(item, startMs)` — and passes **no** start position when there is none, since an explicit 0 would pin a live stream to the start of its window instead of the live edge. Subtitles follow for free: the ticker reads `currentPosition`.

### `web/` — the D-pad cursor and chrome
- `CursorLayout` (FrameLayout) is the input router: it intercepts key events in `dispatchKeyEvent` and dispatches D-pad/OK/BACK/MENU to the cursor or chrome, and paints the cursor dot. This is where the remote-control scheme lives — see the control tables in the Milestone A spec/plan under `docs/superpowers/`. It consumes BACK's `ACTION_DOWN` without `startTracking`, so the Activity's back-tracking never fires `onBackPressed`; the **root BACK** (no chrome, no WebView history) is routed out via the `onExitPage` callback instead → `confirmCloseTab` (a "Close this page?" dialog that blanks the WebView and returns home). BACK is **tap-versus-hold**: the tap chain above is unchanged, but a 500ms hold fires `onLongBack` instead, which reveals the chrome bar. The routing is the **pure** `BackGesture` (`decide(action, alreadyDown, longPressed, barVisible)` → arm / begin-without-arming / ignore / run-tap-chain / swallow; it takes the key action as a raw `Int` to stay Android-free); `CursorLayout` keeps the `Handler` and flags and just applies the decision. `onLongBack` returns **Boolean** — a refused hold (fullscreen) leaves the long-press flag false, so its release still runs the tap chain.
- `CursorController` synthesizes `MotionEvent`s (hover/down/up) onto the WebView to emulate a mouse; geometry (acceleration, edge detection) is the **pure** `CursorGeometry`. OK long-press toggles CURSOR/FOCUS mode. Holding the D-pad into the 48dp top/bottom edge zone scrolls, and it scrolls by **dispatching a mouse wheel** (`ACTION_SCROLL` + `AXIS_VSCROLL`, `SOURCE_MOUSE`) at the cursor rather than calling `webView.scrollBy`: `scrollBy` only ever moves the document, so a cookie dialog with its own scroller — fixed, often in a cross-origin iframe — could not be reached at all (#31). A wheel is hit-tested at the pointer and walks the scroll chain out from whatever sits under it, so the **pure** `CursorGeometry.wheelStep` needs no "can the page scroll" gate and no overshoot pin — Chromium clamps each scroller itself. One tick is 128 CSS px in this WebView (measured on the TV); `WHEEL_TICKS_PER_FRAME` keeps the old 24px-per-frame feel and fractional ticks are honoured. `CursorGeometry.clamp` stops the cursor on the view's **last** pixel (`height - 1`), not at `height`: edge scrolling pins it there, and `y == height` is one pixel past the page, where the wheel is hit-tested onto nothing and falls through to the document — so no inner scroller was ever reached once the cursor was pinned at the bottom (#31). A wheel cannot scroll `overflow: hidden`, though, and that is what a consent dialog taller than the 540 CSS px viewport sits in: Quantcast centres it in a fixed `overflow: hidden` box whose own text area never overflows, so the wheel falls through to the document and the buttons stay below the screen (#31, antenna.gr). Each edge-scroll frame therefore also runs the **pure** `ClippedOverlayScroll` script (`evaluateJavascript`) — the programmatic scroll keyboard focus does on a desktop: it walks out from the element under the cursor, stops at the first box with room left in that direction, leaves a user-scrollable one to the wheel, and `scrollBy`s a clipped one — but only under a `position: fixed` ancestor, and the walk ends at that ancestor, so in-page carousels, truncated cards and an SPA's `100vh` `overflow: hidden` app root (reached from a fixed bottom nav) keep their clipping, and never `html`/`body`, so a scroll-locked page stays put. It acts only while the box has room in that direction, so both ends are clamped and holding the top edge scrolls the dialog back to its start. The cursor is floored to whole CSS px before `elementFromPoint`, which rounds: the last row at 2x is y = 539.5, and rounding lands off the page. **Limit:** `evaluateJavascript` reaches the main frame only, so a CMP inside a cross-origin iframe is not helped by this and still depends on the wheel.
- `ChromeController` / `ChromeVisibility` manage the address bar, summoned with **MENU or a BACK hold** (500ms; the hold timer never arms if the bar is already visible). The bar is **only ever opened for interaction**, so there is no passive on-load reveal and no idle auto-hide: it stays up while the user types/navigates and closes on BACK/MENU/submit. During HTML5 fullscreen `MainActivity`'s `onLongBack` **refuses** the reveal (returns false — the bar would sit under the video), which leaves `backLongPressed` false so the release falls through to the normal BACK chain and exits fullscreen. `UrlNormalizer` turns bar text into an address **or a search**: `resolve(text, engine)` loads text that reads as a host or URL as an address (text with an explicit scheme and a host is always one, even a dotless `http://nas:5000/`) and sends anything else (whitespace, no dot, non-Latin words) to the chosen **pure** `SearchEngine`'s results page, percent-encoded as UTF-8; it is null only for blank input. Both address fields (the bar and home's) submit through it, reading `settings.get().searchEngine` at submit time, and still go through `openUrl`, so a search counts as a user navigation for the ad-block gate. The ★ favorite button **toggles** the current page (add/remove) and shows the filled star in `accent` when the page is saved, the outline star otherwise — see `MainActivity.toggleCurrentFavorite` / `updateFavoriteIcon`.
- **The bar is a floating capsule** (`#chromeBar`: 60dp tall, 16dp from the top, 32dp from the sides, fully rounded, elevated; no blur — that needs API 31 — so the fill is a touch more opaque). Left to right, which is also the D-pad order: Back, Reload, Home │ address pill │ ★ Favorite, ad-block shield, History, Downloads, ⋯ (the page menu, below). The icons are the app's own 24dp line vectors (`ic_back`, `ic_reload`, `ic_home`, `ic_star`/`ic_star_filled`, `ic_shield`, `ic_history`, `ic_download`, `ic_more`, `ic_lock`), never `@android:drawable` glyphs. Icon buttons share `Widget.Mrowser.BarIcon`: 44dp, no fill at rest; focused, a white disc (`bar_icon_bg`), a dark glyph (`color/bar_icon_tint`) and a 1.08 scale (`animator/bar_focus_scale`). A saved star and an allowlisted shield are tinted plain `accent`, which stays red on the white disc too. The shield is a focusable `FrameLayout` (`adBlockButton`) around an `ImageView` and a count **badge** (`adBlockCount`, top-right, hidden at 0, accent while focused — both children `duplicateParentState`); its `contentDescription` carries the count. **Focus stays in the bar:** Back's `nextFocusLeft`, ⋯'s `nextFocusRight` (the last control) and every control's up/down point at themselves, and the URL field's key listener sends LEFT/RIGHT to its neighbours instead of walking the caret through the URL (typing happens in the IME, which takes the D-pad itself). Opening still focuses the URL field. `ChromeController` slides the bar by its height **plus its top margin**, so it clears the screen.
- **The page menu** (#64): ⋯ (`moreButton`) opens `PageMenu` for the current page's site (`SiteSettings.site` — the registrable domain of an http(s) URL; no page → the Toast "Open a page first."). It is a focusable `PopupWindow` (`page_menu.xml`, 380dp, anchored below the bar's right end; `page_menu_bg` is the **window's** background drawable, not the layout's, since the 12dp elevation's shadow follows the window background's outline and a transparent one casts none) rather than a view in the bar's window: its own window keeps the D-pad inside while it is open, and BACK, which the popup handles itself, closes it and hands the main window its focus back — still on ⋯. Two rows in the settings style: **Desktop site** (a switch row, activated for on; OK toggles it, stores the choice and reloads through `reloadForUserAgent`, the panel staying open) and **Zoom**, **one** focus target used as a slider — its key listener consumes LEFT/RIGHT on both actions and steps the zoom on each `ACTION_DOWN` (repeats too), OK resets it to 100%, and the − / + only show it, dimmed to 0.35 at 50% and 200% — so no press is a dead end. A dim line says "Remembered for <site>". `hideAllOverlays`, the error screen and HTML5 fullscreen entry close it, and so does a navigation to another site (`PageMenu.onNavigate` from `onPageStarted`: the panel is bound to the site it opened with, and would otherwise store that site's choices over a page they do not apply to); the Desktop toggle's own reload and a link within the site leave it open.
- **Desktop site** is a User-Agent: the **pure** `DesktopUserAgent.from(defaultUa)` rewrites the WebView's own string to desktop Linux (`X11; Linux x86_64`), drops `; wv`, `Mobile ` and `Version/4.0`, and keeps the real Chrome/WebKit versions. A site's choice is `SiteSettings.wantsDesktop` (its per-site override, else `desktopByDefault`). The agent has to be in place **before** the main-frame request, and setting it never reloads, so `MainActivity` sets it at every load it starts — `loadPage` (`openUrl` and the rest), `reloadPage`, and the pop-up relay's `beforeLoad`. A navigation the page starts goes through `userAgentGate` in `shouldOverrideUrlLoading`: when its site wants the other agent, the navigation is **cancelled and re-issued** (posted `loadPage`) with that agent, and with the `Referer` the cancelled one would have carried — `loadUrl(url, headers)`, from the current page through the **pure** `Referrer` (strict-origin-when-cross-origin, as a download's); a user-typed load sends none. A re-issued navigation that turns out to be a download never commits, so `onDownloadOffered` (for the load in progress, `startedUrl`) gives the page that stays its own agent back, after the listener's `userAgent` has been taken for the file. `onPageStarted` is the safety net for loads the gate never sees (back/forward, a POST): wrong agent → set it and reload. Both go through the **pure** `UserAgentSwitch` — one switch **per site between user navigations** — so a redirect or script ping-pong between a desktop-preference and a mobile-preference site cannot loop reloads. A user navigation resets it: `openUrl`, the menu's toggle, every user BACK that goes back a page (the page's BACK through `CursorLayout.onHistoryBack`, the bar's Back and the error screen's Go back through `goBackByUser` — once per press, so it stays bounded; without it A(desktop)→B(mobile)→A, then BACK twice, landed on A with the mobile agent, its switch spent on the way forward), and in the gate a click, which on API 24+ is `hasGesture && !isRedirect` (a redirect keeps its click's gesture flag, and counting it as fresh would let a ping-pong reset the guard on every hop). API 23 has no gesture flag, so the legacy overload passes false and the cursor's **page tap** (`CursorLayout.onPageTap`) resets the guard instead. A download retry asks with the agent its **source page's** site would get now (`DownloadRunner`'s `userAgent(downloads.pageUrl(id) ?: url)` — the page recorded for the Referer; the file's own URL only when none was), since a file on a CDN host has no per-site choice of its own.
- **Zoom** is CSS `zoom` on the root element, the **pure** `PageZoom.script` run by `evaluateJavascript` (Chrome's steps 50–200%, `stepUp`/`stepDown` snap to them): the whole page scales and reflows, the cursor still hits what it is drawn over, and changing it **never reloads**. It marks the element with `data-mrowser-zoom`, and 100% removes the property only where that marker is, so a page's own `zoom` is left alone. The document is new on every load, so `applyZoomFor(url)` re-applies the site's zoom at `onPageStarted` (best effort — the old document may still be there), `onPageCommitVisible` and `onPageFinished`.
- **Per-site choices** are keyed by registrable domain (`RegistrableDomain`), so `m.` and `www.` share one. The **pure** `SiteSettings` keeps both maps to what differs from the default: `withZoom` removes a site set back to 100, `withDesktop` removes a choice equal to `desktopByDefault`, and flipping the default runs `pruneDesktop`, so a stale entry never shadows a later default.
- **The address pill shows the page, not just its URL:** the **pure** `UrlDisplay` splits an http(s) URL into a secure flag, a lead, the host and the rest; `MainActivity.showPageUrl` colours the host white and the rest `url_dim`, and puts the grey `ic_lock` in the field's start slot for https. An https URL drops its `https://` (the lock stands in for it) and any other scheme keeps it, so the text **still submits to the same page** through `UrlNormalizer` — a test pins that round trip. The first user edit strips the colours and the lock (a `TextWatcher`, muted while `showPageUrl` writes); a non-web URL (`about:blank`) is shown as it is.
- `ExternalSchemePolicy` (**pure**) decides each navigation: a scheme the WebView resolves itself (`http`, `https`, `file`, `data`, `blob`, `about`, `javascript`) loads normally; anything else (`obtainium://`, `intent://`, `market://`, `mailto:`) is an app's, and a `WebView` left to load it dead-ends on `net::ERR_UNKNOWN_URL_SCHEME`. A **clicked** one is handed to the system, one the page fired **by itself** is swallowed silently. `ExternalIntentLauncher` is the Android half: `Intent.parseUri` (which covers plain custom schemes too), then **hardening** — `addCategory(BROWSABLE)`, `component = null`, `selector = null`, URI-permission flags stripped — so a page cannot use the browser as a caller to reach components other apps never exported for links. An `intent://` URL's `browser_fallback_url` is loaded in the page when nothing can open the link, vetted through `IncomingUrl` first (it is page-supplied too). Pre-API-24 has no gesture flag, so the legacy `shouldOverrideUrlLoading` overload treats navigations as user-initiated rather than dead-ending every app link.
- `BrowserWebChromeClient` handles HTML5 fullscreen video, forwards page titles (`onReceivedTitle`) to record browsing history, and answers `onCreateWindow` by relaying the window into the current WebView (there are no tabs): a throwaway relay `WebView` receives the pending navigation purely to read its URL, which never reaches the opener and is then loaded here — unless `AdBlocker.isBlockedPopup` says it is a listed ad host, in which case it is refused and counted. The `isUserGesture` flag is ignored on purpose — see `adblock/`. The **Block pop-ups** setting gates only that list check; Off opens whatever was clicked. A pop-up aimed at a non-web scheme goes through `ExternalSchemePolicy` rather than `loadUrl` (which would hit the error page).
- **Loading feedback and the error screen.** The WebView's main-frame signals reach `MainActivity` through one interface, `PageLoadEvents` (its `pageEvents` object): `onStarting` (from `shouldOverrideUrlLoading`, the earliest sign of a click, and `onPageStarted`), `onCommitVisible`, `onMainFrameError`, `onMainFrameSslError` (the SSL error's URL is the main frame's — compared with the **pure** `MainFrameUrl.same`, since a typed `https://x.com` is reported back as `https://x.com/`; the error is still always `cancel()`ed, never proceeded), `onMainFrameHttpError` (status ≥ 400), `onReloadNotResent` and `onRendererGone`; progress comes from `BrowserWebChromeClient.onProgressChanged`. The **pure** `PageLoad` reducer turns them into the 3dp accent **loading line** (scaled from the left, fades once at the end) and `CursorLayout.busy`, a rotating accent **busy ring** round the cursor dot until the page is first visible; a 30s timeout ends any load that never reports an end, so nothing keeps spinning. A reload of a form's result (the bar's Reload, the page menu's Desktop site, the User-Agent safety net — a cross-site POST never reaches `shouldOverrideUrlLoading`) asks `onFormResubmission`: `SniffingWebViewClient` always answers `dontResend` (a form is never posted again) and reports `onReloadNotResent`, which ends the load as `Finished` — no start, finish or error would follow, and the page is still there as it was. `onStarting` raises feedback only for http(s) URLs (the about:blank of close-tab/home shows none); the app's own loads — `openUrl`, the bar's Back/Reload, Try again, Go back — apply `Started` unconditionally and end through the finish like any other. A start for the URL the last `Started` began (`startedUrl`, matched with `MainFrameUrl.same`) is `PageLoadEvent.StartedAgain`: a clicked link reports `shouldOverrideUrlLoading` first and `onPageStarted` only at commit, and a second `Started` there snapped the line back to 0 and re-armed the ring, so `StartedAgain` leaves a running load alone (with nothing loading it is a plain `Started`). Every app-initiated `loadUrl` of a web page goes through `MainActivity.loadPage`, which first calls `SniffingWebViewClient.expectNavigation(url)` (the pop-up relay does the same through `BrowserWebChromeClient.beforeLoad`): such a load reaches no `shouldOverrideUrlLoading`, and a WebView may post `onPageStarted` only at commit, which a refused certificate never reaches — without it the certificate error would not be the main frame's and the page would stay blank. The **pure** `PageError.classify` maps the `net::ERR_*` description (the code only as a fallback) to a `PageErrorKind`, and returns **null for a cancelled navigation** (`ERR_ABORTED` from our own ad cancel, a download, `ERR_UNKNOWN_URL_SCHEME`), which must never show the screen. `PageErrorView` is the **error screen**: native, not HTML, outside `CursorLayout` (whose key routing would take the D-pad — so the capsule bar cannot be summoned over it; its buttons are the way out), over the page and under the overlays. Icon, "This page didn't load", a reason naming the host, a dim code (`ERR_NAME_NOT_RESOLVED`, `HTTP 503`), and **Try again** (focused), **Go back** (only when it leads somewhere other than home) and **Home** (`closeToHome`, shared with the close-tab dialog). BACK = Go back, else Home. What Try again and Go back do is the **pure** `ErrorNavigation`, from plain facts (never-committed, `clearHistoryOnLoad`, `webView.url`, the failed URL, `canGoBack()`). The deciding fact is whether the failed load **ever committed**, never the error's kind: only a refused certificate (`onMainFrameSslError`, cancelled before commit) leaves the page the link was clicked on current, so Go back **uncovers** it and Try again `loadUrl`s the failed URL; every `onReceivedError` failure — `ERR_SSL_*`/`ERR_CERT_*` handshake failures included, which are "Not secure" too — commits Chromium's grey error page as an entry with the failed URL, so Go back is `goBack()` and Try again `reload()`s (uncovering one would leave the grey page on screen). A fresh tab (opened from home) has no Go back either way: its back-stack is cleared at finish, and since the error page commits only after the error is reported, the button is refreshed in `onLoaded` so it agrees with BACK. Any new navigation (`onStarting`) hides it. An HTTP error is often the site's own page, so a 4xx/5xx shows **Server error** only when the page is empty (`PageError.EMPTY_PAGE_SCRIPT`) at **two checks in a row** (`PageError.EMPTY_CHECKS`, `emptyVerdict`), the first **1s after** it finished and the second 1s after that, run only if the first said empty — an app shell served with an error status is still empty at the finish, and one showing only a CSS spinner at the first check is not covered. Any new navigation, and `onDestroy`, cancels both. `onRenderProcessGone` (API 26+) returns true, destroys the dead WebView and `recreate()`s the Activity; the companion's `crashedUrl` makes the new instance show **Page crashed** for it ("The page at <host> stopped working", or "<host> was closed to free up memory" when `RenderProcessGoneDetail.didCrash()` is false — the companion's `rendererKilled`) and load **nothing** by itself (not even the launch intent's link), so a page that kills the renderer cannot loop — only Try again reopens it. `onDestroy` clears both when the Activity is finishing for good (`isFinishing && !isChangingConfigurations`; `recreate()` is a configuration change), so a pending crash screen cannot greet a later cold launch.

### `adblock/` — host-list ad blocking and the navigation gate
Issue #38. A bundled domain list (`res/raw/blocklist.txt`: OISD small ∪ HaGeZi Pop-Up Ads, both GPL-3.0, regenerated by `scripts/update-blocklist.sh` and the weekly `blocklist.yml` workflow; attribution in `THIRD-PARTY-NOTICES.md`) is loaded on a background thread into the **pure** `BlockList` — sorted 64-bit FNV-1a hashes, `contains(host)` walks the host's suffixes down to but excluding the TLD. Until it loads everything passes. Two **pure** decisions: `AdBlockPolicy` for sub-resources (in order: off → allowlisted → main frame → media the sniffer cares about → first-party by `RegistrableDomain` → list), answered with a typed stand-in from the **pure** `BlockedResponse` (1×1 GIF / empty HTML / empty JS / empty text, from the `Accept` header then extension); and `NavigationPolicy` for a top-level destination — a `window.open` target peeked through the chrome client's relay, or an in-page navigation in `shouldOverrideUrlLoading` — which is **cancelled so the page stays put**, never served an empty body. There is no gesture heuristic: with `javaScriptCanOpenWindowsAutomatically=false` Chromium refuses gestureless opens before `onCreateWindow` (`AwContentBrowserClient::CanCreateWindow`), and click-hijack scripts fire inside the user's click, so only the destination can be judged (uBlock Origin's `$popup` model). The navigation gate exempts two cases a straight destination check over-refused on real hardware: a navigation the user initiated (URL bar, home, favorite, incoming intent — `AdBlocker.onUserNavigation()`, cleared on the next `onPageStarted`/`onPageFinished` so it covers only that load's redirect chain, not what the page does afterward) and a navigation that stays within the current registrable domain (same site, different page). A script-initiated navigation to a listed **third-party** host is still refused either way — that is the feature. A pop-up destination is never user-initiated (`isBlockedPopup` always passes `userInitiated = false`). `AdBlocker` is the one Android class: volatile list + page host + user-navigation flag, atomic per-page counter, settings via provider lambdas (`blockAds` gates interception and navigations, `blockPopups` gates the relay, `adsAllowedOn` is the per-site allowlist keyed by registrable domain). API 24+ also registers a `ServiceWorkerClient`, since service-worker fetches bypass `WebViewClient`. UI: the chrome-bar shield (count label, click = allow/block ads on this site + reload, tinted `accent` when allowed), Settings rows **Block ads** and **Ad block lists** (attribution dialog from the list header). `UrlHost` and `RegistrableDomain` live in `web/` next to `UrlNormalizer` so `stream/` and `adblock/` share them without a cycle. The canary test `BlockListCanaryTest` reads the real list and fails CI if a pop-under network drops out or a video-CDN apex creeps in. Host-level only: no cosmetic hiding, and same-origin ads (YouTube-style) are not blockable this way.

### `download/` — downloads, the Downloads page, installing APKs

A page only ever **offers** a file; nothing is saved until the user presses **Download**. The
`WebView`'s `DownloadListener` calls `MainActivity.onDownloadOffered`, which first tells
`StreamSniffer.onDownload(url)` — a video file sent as an attachment was also seen as a request,
and dropping its candidates keeps the player from opening on it 1.5s later — then takes only
`http`/`https` (the **pure** `DownloadRequest.isSupported`; `blob:`/`data:` are the page's own
memory, which `DownloadManager` cannot fetch, so they get a Toast) and shows
`DownloadConfirmDialog` ("Download this file?": name, size via `ByteSize` or "Unknown size", the
link's host). **One confirm at a time**, so a page cannot stack prompts — and **no repeats after a
decline**: once the user turns a confirm down (Cancel, BACK, outside), the **pure**
`DownloadOfferGate` ignores every further offer until the next `onPageStarted` (a download never
commits, so a page firing `location.href = 'x.apk'` on a timer never gets one) or the user's own
cursor click on the page (`CursorLayout.onPageTap`), with one Toast on the first offer ignored.
Without it such a page brought the dialog back after every Cancel and the user could reach
neither the bar nor Home. Download is focused but **ignores presses for 500ms** (the **pure**
`ConfirmDelay`): a page can fire a download from the user's own OK press, and a repeat of that
press must not land on it. The delay runs from when the dialog's **window gains focus**
(`OnWindowFocusChangeListener` on its decor) and restarts on every regain, not from `onShow` — a
confirm opened while the player is in front would otherwise be armed when the user comes back.
Its click listener is set in `onShow`, so an early press neither confirms nor dismisses.

The sniffer **holds a main-frame file** (`StreamSniffer.mainFrameFile`): a top-level request for a
progressive file may be a page the WebView will show or an attachment the listener gets, and the
listener can report a different URL (a redirect to a signed CDN link) or fire after the grace
window. So that file becomes a candidate only when `onPageStarted` commits the same URL as the
page (`MainFrameUrl.same`); a download drops it.

**Naming:** `URLUtil.guessFileName(url, disposition, mime)` in the glue, with a generic MIME
(`application/octet-stream`, `application/force-download`, …) dropped first by the **pure**
`DownloadFileName.cleanMime` so it does not decide the extension; then the **pure**
`DownloadFileName.sanitize` makes one safe name that lands directly in Downloads (last path
segment only, control and bidi characters dropped, `:*?"<>|` → `_`, at most 120 characters and
240 UTF-8 bytes with the extension kept, `download` when nothing is left). The list shows the
name the file really got (DownloadManager suffixes a clash) from `COLUMN_LOCAL_URI` through
`DownloadFileName.displayName` — never `COLUMN_LOCAL_FILENAME`, which throws on targetSdk ≥ 24.

**Headers** (the **pure** `DownloadRequest.headers`): `Cookie` from `CookieManager` for the
download URL, the `User-Agent` the listener reported (so desktop mode is honoured), and a
`Referer` from the page as it was when the file was offered, trimmed the way a browser's default
`strict-origin-when-cross-origin` does (the **pure** `web/Referrer`, shared with the User-Agent
gate's re-issued navigation): the page without fragment or user info to its own origin, only its
origin (`scheme://host[:port]/`) cross-origin, nothing from https to http.

`Downloader` is the Android wrapper over the system `DownloadManager` — the one `ApkDownloader`
builds on: enqueue to public `Downloads/` (`setDestinationInExternalPublicDir`,
`VISIBLE_NOTIFY_COMPLETED`, MIME set; below API 29 `ensureStoragePermission` runs first),
`query`, `remove`, `contentUri`, `fileUri`, `fileExists`. Every call logs and degrades instead of
throwing — a missing download service or a locked-down Downloads provider is realistic on TV
boxes, and the list polls these calls. `query` returns **null** when the manager could not be
asked and an empty list when it has forgotten everything, so the two are never confused.

`DownloadsController` (Android glue) keeps `filesDir/downloads.json` (`JsonDownloadsStore` over the
**pure** `DownloadsJson` / `DownloadsOps`): what DownloadManager does not hold — each id's page URL
(Retry's Referer, the row's "from" host) and the ids hidden from the list. Ids the manager has
forgotten are pruned, **only after a successful query**: a failed one would otherwise forget every
page. **`DownloadManager.remove()` deletes the file**, so only **Cancel download** and **Delete
file** reach `DownloadsController.remove`; Remove from list, Clear finished and a retried row's old
entry only **hide** ids. A file found deleted elsewhere is remembered for the process
(`markMissing`) and its row reads "File removed".

**Polling, no receiver:** one query a second on the UI handler, scheduled only while something is
active or the Downloads page is open (`isPageOpen`), kicked when a download starts, a row is
hidden or the Activity resumes, stopped in `onPause`/`onDestroy`. A failed query keeps the last
snapshot. Each poll becomes a `DownloadsSnapshot` built by the **pure** `DownloadList` (active rows
first, then newest; the summary; which downloads just finished or just failed — `justFinished` /
`justFailed`, active at the last poll), `DownloadSpeed` (smoothed
bytes/s, null until two samples and again once a stall decays it below 1 KB/s), `DownloadText`
(the English row and chip text — never "-1", over 100% or a time left from no speed) and
`DownloadRows`.

**Where it shows:** a **download chip** bottom-left (32dp from the left, 36dp from the bottom; the
play chip keeps bottom centre) — the name and percent, "2 downloads · 37%", then "Downloaded ·
name" for 5s, or "Download failed · name" (a failure wins over a success in the same poll —
`DownloadText.chipEnded`) — only over the page, and a cursor click on it opens the Downloads page
(`CursorLayout.downloadChip`); the bar's **Downloads** button (`DownloadsButton`, an `ImageButton`
that draws a 2dp `ring_track` circle and an accent arc of overall progress while anything runs);
and home's Downloads pill with its accent dot.

**The Downloads page** (`DownloadsView`) is the **fourth overlay**, focus-modal like History (see
`home/`). `render` runs on every poll, so it **updates rows in place** while the list is the same
ids in the same order and rebuilds only when that changes, then re-seats focus on the same
download's row (else the first) — a destroyed focused row hands focus to the page behind (#32).
Clear finished stays visible with nothing to clear for the same reason, and the empty line shows
from the start, so the page is never just a header before the first poll answers.

**Row actions** (`DownloadRunner`, over the **pure** `DownloadActions`). OK runs the primary: a
finished **video** (`video/*` or a video extension) plays in `PlayerActivity` from its
`content://` URI (a `PlaybackRequest` with no headers or subtitles, so resume works by that URL);
an **APK** goes to `ApkInstaller`; anything else is `ACTION_VIEW` with the read grant (no app →
Toast); a failed row **Retries** — a new download of the same URL with fresh Cookie and UA and the
stored Referer, the failed row hidden. A failed row has no local file, so its name may be the
title ("mrowser 1.5.0"); the **pure** `DownloadFileName.withExtension` gives it an extension from
the MIME type, else from the URL's last path segment, so a retried APK still ends in `.apk`. Play/Install/Open check `Downloader.fileExists` first. OK
on a row with nothing to run (running, or its file gone), a hold of OK, or MENU opens the
**options**: the primary, Cancel download (active rows), **Delete file** (finished rows; a red
label, then a "Delete this file?" confirm whose Delete is `DestructiveButton`), Remove from list,
Copy link. `DownloadActions.effect` guards Cancel to active rows and Delete file to successful
ones, and the runner re-queries the download when an option is picked, so a Cancel chosen after
the download finished cannot delete the file. Cancel and Delete file act **only on that fresh
answer** (`DownloadActions.stateFor`): when the re-query fails or no longer has the id they Toast
"Couldn't check this download" instead of falling back to the row as it was when the dialog
opened; the other options keep that fallback.

**`ApkInstaller`** hands an APK to Android's installer, which shows the app and asks the user to
confirm. Only a user's press reaches it (Install on a row) — never a page; a page's download only
ever lands in the list. The manifest declares `REQUEST_INSTALL_PACKAGES`. On API 26+ without
`canRequestPackageInstalls()` a dialog explains, opens mrowser's
`ACTION_MANAGE_UNKNOWN_APP_SOURCES` page and stops — coming back does not install; the user
presses Install again. The installer gets a `content://` URI with `FLAG_GRANT_READ_URI_PERMISSION`
from API 24 and a `file://` one below (the pre-N installer reads only `file:`). A missing file or
no installer → Toast.

### `update/` — the update channel

mrowser is sideload-only, so nothing tells a user on an old APK that a new release exists. On
each process launch `MainActivity` calls `UpdateController.checkIfDue`, which asks GitHub for
`/releases/latest` (stable only — that endpoint excludes drafts and prereleases) **at most once
every 24h**, guarded by the **pure** `UpdateCheckPolicy`. The request carries a `User-Agent`
(GitHub 403s API calls without one) and an `If-None-Match` from the cached ETag, so a repeat
check is a 304 costing no rate-limit quota — the unauthenticated limit is 60/hr **per IP**, and
CGNAT puts many users behind one. The body is parsed by the **pure** `ReleaseJson`, which
requires **exactly one** `.apk` asset and refuses drafts/prereleases, and cached to
`filesDir/update.json` through `UpdateStateRepository` / `JsonUpdateStore` over the **pure**
`UpdateJson`. Every failure logs and returns — there is no user-visible error anywhere in the
check, so a box where `api.github.com` is unreachable behaves exactly as before.

`UpdateController` itself has **no Android imports** (network call, both thread hops and the
clock are injected, like `StreamSniffer`) and is unit-tested. A failed check deliberately does
**not** bump `lastCheckedAt`, so a transient outage costs one retry rather than a day of silence.

The banner is a quiet accent-text button at the **bottom-left of the home overlay**
(`HomeView.showUpdate`), drawn from the cache on the first frame and again if the check turns
something up. It has no dismiss and stores no "seen" flag: the **pure** `UpdateCheckPolicy.bannerFor`
compares the cached release against `PackageManager`'s `versionName` through the **pure**
`VersionCompare`, so installing the new APK clears the line by itself.

`UpdateDialog` shows the notes (plain text — never the WebView), the size (**pure** `ByteSize`)
and a **Download**. `ApkDownloader` hands the URL — vetted by the **pure** `DownloadUrl` to https
on `github.com`/`*.githubusercontent.com` — to `Downloader` (see `download/`), which saves it
through the system `DownloadManager` to public `Downloads/mrowser-<version>.apk`. Being an
ordinary download, it shows on the **Downloads page** (and the chip and bar ring) with
**Install**, which hands it to Android's installer through `ApkInstaller`; a file manager works
too. Saving is all the update channel does — the install is the user's press there. Storage is
`WRITE_EXTERNAL_STORAGE` with `android:maxSdkVersion="28"` (scoped storage makes it free from
API 29), asked for only on the Download tap. The dialog's progress line is **polled** on the UI
handler rather than watched via `ACTION_DOWNLOAD_COMPLETE`, which on targetSdk 34 would need
`RECEIVER_EXPORTED`. When the permission is denied or `DownloadManager` is missing, the dialog
falls back to the release URL plus the Obtainium route.

### `home/` + `data/` — home screen, favorites, history, settings
- `HomeView` is the launch overlay (favorites grid + URL entry); `FavoriteDialog` edits entries. Its background **cycles**: one `GradientDrawable` whose two colours are rewritten on a tick, walking forever through the **pure** `HomeBackgrounds.ALL` palettes (20s per neighbouring pair, 120s per lap) via the **pure** `blend`. `indexFor(seed)` picks the starting palette once per launch in `bind`; the `ValueAnimator` lives in `show`/`hide` — leaving it running would tick behind the WebView and through playback — and is cancelled in `onDetachedFromWindow`. Updates are throttled to 10fps (the colours crawl, so 60fps redraws of the whole overlay buy nothing). Bottom stops carry the colour and are spread far enough apart for the fade to be visible at all; top stops stay near-black so text keeps its contrast wherever the cycle is caught. Both properties are pinned by tests. The header is the capsule bar's shapes: a 48dp address pill (`home_field_bg`, `ic_search`), a History pill (`Widget.Mrowser.Pill`), a Downloads pill (with an accent dot while anything downloads — `HomeView.showDownloadsActive`) and a settings circle (`circle_bg`, line-style `ic_settings`); the header row and the root turn `clipToPadding`/`clipChildren` off so the focus scale is not cut. Favorite cards are the card surface with a hairline; focus is a 3dp white ring (`card_bg`) plus the scale 1.08, the lift and the medium white title `HomeView`'s focus listener adds. The update line is a quiet pill with an accent dot. `HistoryView` is the history overlay (a vertical list of visited sites; open / clear-all / long-press-to-favorite): rows on `row_bg`, the URL as `UrlDisplay` shows it (no `https://`), and Clear all a destructive pill (`Widget.Mrowser.Pill.Danger`) that still acts at once.
- **Reordering favorites** (#47): `FavoriteDialog` (a card's long-press) also moves the entry. Its `◀ Move left` / `Move right ▶` row lives inside the dialog's custom view (all three AlertDialog buttons are taken), so the dialog stays open across presses: each press moves the entry one place in list order (wrapping rows in the 4-column grid), rebuilds the grid behind the dialog, and enables/disables the buttons from the **pure** `FavoritesOps.canMove`. `HomeView.refresh(focusUrl)` seats focus on that url's card after the rebuild, so when the dialog closes — Save, Cancel or BACK — the D-pad is on the moved/edited card, never the URL pill or the page behind (see Focus recovery).
- Favorites use the repository pattern: `FavoritesRepository` interface, `JsonFavoritesStore` implementation persisting to `filesDir/favorites.json`. The **pure** `FavoritesOps` (list transforms, including `move` — one step earlier/later, clamped at the ends) and `FavoritesJson` (serialization) hold all the logic; the store is just file I/O. The **pure** `DefaultFavorites` (YouTube, Google) is seeded once on first launch, guarded by the `seeded` flag on `Settings` rather than an is-empty check, so a user who deletes them doesn't get them back.
- **Favorites export/import** (#48, favorites only — not settings). **Export** writes a **fixed** file, `Downloads/mrowser-favorites.json`, with **no picker** (on Fire OS a document picker can't be D-padded anywhere but Downloads, and some boxes ship none): API 29+ through `MediaStore.Downloads`, overwriting this install's earlier export (`"wt"`) instead of piling up "(1)" copies; below 29 the public directory, with `WRITE_EXTERNAL_STORAGE` (the updater's, `maxSdkVersion=28`) asked at tap time through `ensureStoragePermission`. **Import** can't mirror that — from Android 11 an app can't read a non-media file in Downloads that another install wrote, which is the whole new-device case — so it uses `ACTION_OPEN_DOCUMENT` (`*/*`; providers disagree on a `.json`'s type) opened in Downloads via `EXTRA_INITIAL_URI` (API 26+). **Many TV boxes have no picker:** Android TV builds without DocumentsUI still resolve the intent — to `com.android.tv.frameworkpackagestubs`' DocumentsStub, which toasts "You don't have an app that can do this" and returns (the KTC TV does this) — so launching can't throw `ActivityNotFoundException`. The intent is therefore resolved first (a `<queries>` entry makes DocumentsUI visible under package visibility) and the **pure** `DocumentPicker` treats the stub, or nothing, as no picker → the app's own dialog. An "Open with mrowser" VIEW route was tried for such boxes and dropped: the KTC's only file manager (`com.kgzn.filemanager`) can't hand an unknown file type to another app. The picked file is read off the main thread under an 8 MiB cap (a Firefox bookmarks.html embeds a favicon per bookmark). `FavoritesBackupFile` is the Android glue; the **pure** `FavoritesBackup` owns the format: `{"app":"mrowser","version":1,"favorites":[…]}`, also accepting a bare array (exactly `favorites.json`), skipping bad entries one by one, keeping only `http`/`https` urls (they go straight to `loadUrl`), and returning null for a file that isn't one. **It also takes a browser's Netscape `bookmarks.html`**: when the text is not JSON, the **pure** `BookmarksHtml` (`looksLike` sniffs the `NETSCAPE-Bookmark-file` doctype or a `<DT><A` entry) reads each `<A>` as a favorite through a hand-written linear scanner, not a regex, because Firefox's `ICON="data:…"` attributes are multi-KB and tags are uppercase, single-quoted or `&amp;`-escaped depending on the browser; folders and `<HR>` are ignored (favorites are flat). `Parsed.source` (`MROWSER` / `BOOKMARKS_HTML`) picks the Toast wording ("…from bookmarks.html…"). One import adds at most **200 new** urls (`FavoritesBackup.capNew`, the **pure** cap: urls already present always pass, the first 200 distinct new ones in file order are kept) and the Toast says how many were left out. The merge is the **pure** `FavoritesOps.merge` (existing entries and order kept, new urls appended in file order, deduped within the import) behind `FavoritesRepository.addAll`. Malformed, empty or unreadable → a Toast and favorites untouched; dropped entries are counted in the "Imported N favorites (M already present, K skipped)" Toast.
- History mirrors the same split: `HistoryRepository` / `JsonHistoryStore` (→ `filesDir/history.json`), with the **pure** `HistoryOps` (dedup-by-url, newest-first, cap 50) and `HistoryJson`. `RelativeTime` (pure) formats the "Nm ago" labels. Recording happens on **page finish** (resolved URL + real title) — not `onPageStarted`, whose pre-redirect URL would leave duplicate rows.
- **Global settings** use the same split: `SettingsRepository` / `JsonSettingsStore` (→ `filesDir/settings.json`) over the **pure** `SettingsJson`; `Settings` is one immutable record (no `Ops` — updates are `copy()`). `SettingsView` is the overlay (reached from a **Settings** gear in the home header) with eleven rows in three sections — Playback, Browsing, Favorites, whose labels are not focusable — (inside a `ScrollView` — they outgrow a 540dp-tall 1080p/320dpi screen; the focused row scrolls into view). A toggle row shows a switch: a plain `View` on `switch_bg` that copies its row's state (`duplicateParentState`), with `SettingsView` **activating the row** for "on" — not a framework `Switch`, which would add a second focus/click target — and the row's content description says On/Off; a picker row shows its value in grey with a chevron. The rows: an auto-open toggle, **match frame rate** and **match resolution** toggles (read by `PlayerActivity`, see above), a **block pop-ups** toggle, a **block ads** toggle, an `AlertDialog` picker for **search engine** (`SearchEngine`: DuckDuckGo by default, Google, Bing, Brave Search, Startpage; first row of Browsing), a **Desktop site by default** toggle (`desktopByDefault`; turning it prunes the per-site choices that now equal it — see the page menu under `web/`), an `AlertDialog` picker for **cursor speed** (`CursorSpeed`, a multiplier over `CursorGeometry`), an **Ad block lists** row that opens the attribution dialog built from the bundled list's header, and **Export favorites** / **Import favorites** (see above; the file work needs the Activity, so the rows call back into `MainActivity` through `SettingsView.bindFavorites`). Every setting is read **live** at use-time via provider lambdas — the auto-open gate in `onStreamAvailable`, `matchFrameRate`/`matchResolution` when a stream's tracks arrive, `blockPopups`/`blockAds`/`adsAllowedOn` through `AdBlocker`, `desktopByDefault`/`desktopOverride`/`zoomBySite` at each load (`wantsDesktop`, `applyZoomFor`), and `cursorSpeed.multiplier` in `CursorController` — so changes apply with no restart and need no change-callback. `SettingsRepository.get()` returns an immutable snapshot, which is why `AdBlocker` may read it from WebView worker threads. `Settings` holds `searchEngine` (the Search engine row, first in Browsing, before Block pop-ups; persisted by id, a missing or unknown id reads as DuckDuckGo) as well as the per-site ad allowlist `adsAllowedOn` (registrable domains, toggled from the chrome-bar shield, no row in `SettingsView`), the page menu's `desktopOverride` (`Map<String, Boolean>`, true = desktop; it can say "mobile here" when the default is desktop) and `zoomBySite` (`Map<String, Int>`, percent) — both by registrable domain, edited only from the page menu — plus `seeded` and `navHintShown` (the one-time hold-BACK Toast, `MainActivity.showNavHintOnce`) — internal bookkeeping, not user preferences, with no row in `SettingsView`.
- **Overlays are focus-modal:** only one of `homeView` / `historyView` / `downloadsView` / `settingsView` is visible at a time. Android's D-pad `focusSearch` is window-global, so a second visible overlay behind the active one steals focus — every transition routes through `MainActivity.hideAllOverlays()` (hides all four, and the page-error screen) before showing one, and closes the page menu. It also **closes the address bar** (`ChromeController.dismiss()`, the pure `ChromeVisibility` `Dismissed` event): a bar left VISIBLE under an overlay is in the same focus search, and the capsule's ★/shield/History sit level with home's History and settings buttons, so RIGHT from home's address field jumped behind the overlay and `OverlayFocus` pulled it back — focus never reached History. `dismiss()` hides at once (the opaque overlay covers it; mid-slide the bar is still focusable) and leaves focus to the overlay; HTML5 fullscreen entry goes through it too. History is reachable from the home overlay **and** the chrome bar (BACK returns to its origin — home, or the page if opened mid-browse, tracked by `historyFromHome`); Downloads likewise, from home's pill **and** the bar button or the download chip (`downloadsFromHome`); settings is reachable only from the home header (BACK → home). The **page-error screen** (`PageErrorView`, see `web/`) is a further focus zone that stands in for the page: it lies under the overlays and never takes focus from one (`show(…, takeFocus = false)` when a load fails while history is open over the page; closing history to the page hands focus to it), and its buttons pin their outward next-focus at themselves so UP/LEFT/RIGHT cannot fall through to `CursorLayout` behind it.
- **Focus recovery:** a synchronous `requestFocus` right after an overlay becomes `VISIBLE` can no-op before the layout pass, leaving nothing focused (dead D-pad). All four overlays' `show()` post `restoreFocus()`, and so does the error screen's. Focus can also end up in the *wrong* subtree: destroying the focused view (`HomeView.refresh` rebuilding the grid after a favorite edit) sends the window's fallback to the root layout's first focusable — `CursorLayout`, **behind** the still-visible overlay — so the D-pad drives the hidden cursor and BACK reaches `onExitPage`. `refresh()` therefore re-seats focus itself when it destroyed its own (guarded on `findFocus()`, so the chrome bar's star button refreshing a hidden home doesn't steal it). As a backstop, `MainActivity.dispatchKeyEvent` re-seats focus and swallows that one keypress whenever focus isn't in the subtree that owns it — the **pure** `OverlayFocus` (settings → history → downloads → home → error screen → page) decides, and `focusZone()` walks up from `currentFocus` to say where it actually is.
- **BACK / exit chain** (`MainActivity.onBackPressed`): settings overlay → hide (→ home); history overlay → hide; downloads overlay → hide (→ home, or the page it was opened over); home overlay → `confirmExit` ("Exit mrowser?" dialog → `finish`); error screen → Go back, or `closeToHome` with no history; browsing → `confirmCloseTab` (via `CursorLayout.onExitPage`). Opening a page from home is a **fresh tab**: `openUrl` sets `clearHistoryOnLoad`, and the first `onPageFinished` calls `webView.clearHistory()` so the opened page is the lone back-stack entry and BACK reaches root immediately.

## Conventions

- **No AndroidX/Compose** beyond Media3. Activities extend the framework `Activity`, UI is XML layouts in `res/layout`, and pure modules are plain Kotlin `object`s/classes with no Android imports. Keep it that way.
- Netflix-style dark theme; brand red is `#E50914`. Colours are named in `colors.xml`, not written into layouts.
- **One focus language, app-wide.** Pills and icon buttons turn white with a dark label and scale up (1.06 pills — `animator/pill_focus_scale`, 1.08 icons — `bar_focus_scale`); **list rows** (settings, history, dialog lists, media3's track lists) never go white: the row-focus fill (`row_focused`) with a soft 50% white outline, the text white; favorite cards a white ring and a lift; text fields the control fill, a step lighter with the accent ring while focused. Red is otherwise kept for state and action (a switch that is on, the saved star, Delete/Exit/Clear all). Colours are tokens in `colors.xml` (`card_surface`, `control`, `field_focused`, `row_focused`, `text_primary`/`_secondary`/`_dim`, …).
- **Dialogs are styled by the theme, never per call site.** Every dialog is a framework `AlertDialog` — both activities', and media3's `TrackSelectionDialogBuilder` (it builds an `android.app.AlertDialog` with theme 0 when AppCompat is absent) — so `Theme.Mrowser`'s `android:alertDialogTheme` → `Theme.Mrowser.Dialog` restyles them all: a 20dp-rounded card (`dialog_background`, min 420dp) drawn **edge to edge — the window is the card**. It has no `<inset>` margin like the framework's `dialog_background_material`: Fire OS draws `AlertDialog`s with its own layout, which put the content in that transparent margin, so the card cropped it on the left (#65). Dropping the inset needed no padding to make up for it: the stock decor pads its content by the window background's padding, and an `InsetDrawable` reports its inset as padding, so the content was always flush with the card's edge — a `<padding>` on the shape or a larger `dialogPreferredPadding` would move it 16dp in. It has white 21sp titles, pill buttons (`Widget.Mrowser.DialogButton`, white + 1.06 scale when focused, no all-caps), rounded 46dp list rows (`dialog_row_bg` as the list selector — a ListView pads its rows by the selector's inset, so they line up with it — and `dialog_view_row_bg` as `selectableItemBackground` for media3's track rows: a view **takes its background's padding as its own**, so that drawable carries the row's text padding too), an accent dot for the checked choice (`listChoiceIndicatorSingle`), and rounded fields (`editTextStyle`). **Android TV draws `AlertDialog`s with the framework's leanback layout** (`alert_dialog_leanback`), not the phone one: buttons are left-aligned in the order positive, negative, gap, neutral, and `buttonBarStyle` lands on the `ButtonBarLayout` itself — so its padding is tuned for that, and it turns `clipToPadding` off, or the focus scale is cut flat (the capsule bar does the same for its end buttons). Only public attributes are used; what they can't reach stays stock: the message is 16sp (its style is private), a single-choice dot sits at the row's start (`select_dialog_singlechoice_material` hard-codes `drawableStart`), and `windowFixedWidth*` are private, so 420dp is a minimum width, not a cap (on the TV a long message still wrapped at 420dp). A view built for a dialog's custom panel must be created from `AlertDialog.Builder.context` (the themed context) to pick up these styles — see `FavoriteDialog`. A **destructive** button (Delete in Edit favorite, Exit in the exit confirm) is the one thing the theme can't single out: `DestructiveButton.apply(dialog, which)` after `show()` gives it red text and an accent focused fill. Pickers with a current value (cursor speed, playback speed, subtitles) are `setSingleChoiceItems`, so the dot marks it and the D-pad starts on it; a pick still dismisses.
- Design docs, specs, and milestone plans live in `docs/superpowers/`. Read the relevant milestone plan before changing cursor input or the handoff pipeline — they document the intended control scheme and edge cases.

## Release & CI

`.github/workflows/build.yml` runs `./gradlew test` + `assembleDebug` on every push/PR (`test-and-debug` job), and builds a **signed** release APK on GitHub Release publish (`release-apk` job, gated by `if: github.event_name == 'release'`) using secrets `KEYSTORE_BASE64`, `STORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD` (decoded into a temporary `keystore.properties`). The `release-apk` job needs `permissions: contents: write` to attach the APK — keep it.

Actions are pinned to commit SHAs (supply-chain safety); `.github/dependabot.yml` opens weekly PRs bumping those pins.

**Releasing:** bump `versionCode` (must increase per release) + `versionName` in `app/build.gradle.kts`, push, then `gh release create vX.Y.Z --prerelease --title … --notes …` — the published event triggers the signed build, which attaches `app-release.apk`. Drop `--prerelease` for a stable release. Remote `origin` = `github.com/m-salehi-v/mrowser` (public — the update channel depends on
unauthenticated access to its releases API). Locally, `keystore.properties` and `release.keystore` are gitignored.
